MAST - Memory-Augmented Storage

Introduction

MAST (Memory Agent Storage Tiers) is an embeddable storage engine purpose-built for AI agent memory. Think of it as “the SQLite of agent memory” – a single-file, zero-server database that combines vector search, full-text search, metadata filtering, graph relationships, and time-tiered compaction into one package.

Why MAST Exists

Every existing agent memory system wraps general-purpose databases – Postgres, Qdrant, Redis – because nothing purpose-built exists. Agent memory has unique requirements:

  • Time-tiered compaction as a first-class primitive. Memories evolve from raw events to distilled patterns to core identity. This should happen at the storage level.
  • Compaction as synthesis, not summarization. “User rejected salesy copy 15 times” compacts into “user hates salesy copy.” This is knowledge creation, not truncation.
  • Hybrid search in a single query. Vector similarity + metadata filters + full-text + tier blending, without orchestrating across multiple databases.
  • Graph relationships alongside flat memories. Entity relationships (user -> prefers -> dark mode) live next to the memories themselves.
  • Embeddable, zero-dependency. pip install a package, no Docker, no server.

Architecture at a Glance

MAST Engine
+-- Storage Layer: redb (single-file ACID, key-value)
+-- Vector Index: usearch HNSW (per-collection, cosine metric)
+-- Full-Text Index: BM25 (per-collection, redb-backed posting lists)
+-- Metadata Index: inverted index (redb-backed posting lists)
+-- Graph Layer: forward/reverse edge indexes for entity relationships
+-- Compaction Engine: pluggable Compactor trait for tier promotion
+-- Serialization: bincode (storage) + serde_json (snapshots)

What MAST Is Not

  • Not a general-purpose database. No SQL. No arbitrary queries.
  • Not a vector database. Vector search is one component of a larger memory system.
  • Not a framework. It does not tell you how to build agents.
  • Not an LLM. It has a pluggable LLM interface for compaction, but ships no model.

Memories

A Memory is the fundamental unit of data in MAST. It combines content, a vector embedding, metadata, tier classification, and lifecycle tracking into a single record.

Memory Struct

#![allow(unused)]
fn main() {
pub struct Memory {
    pub id: Ulid,                          // Time-sortable unique ID
    pub collection: String,                // Namespace (e.g., "user:alice")
    pub content: String,                   // The memory text
    pub embedding: Vec<f32>,               // Vector embedding
    pub metadata: HashMap<String, String>, // Arbitrary key-value pairs
    pub tier: Tier,                        // Core | Active | Background | Archive
    pub created_at: i64,                   // Unix timestamp (seconds)
    pub access_count: u64,                 // Number of times recalled
    pub last_accessed: i64,                // Last recall timestamp
    pub ttl: Option<i64>,                  // Time-to-live in seconds (None = no expiry)
    pub compacted_at: Option<i64>,         // When this memory was compacted
    pub parent_ids: Vec<Ulid>,             // Source memories (compaction provenance)
}
}

Fields in Detail

id

A ULID (Universally Unique Lexicographically Sortable Identifier). Generated automatically on store(). ULIDs are time-sortable, so newer memories have lexicographically greater IDs.

collection

A namespace string that isolates memories. Each collection has its own vector index, full-text index, and graph. See Collections.

content

The raw text of the memory. This is indexed for full-text search and passed to the embedder for vector generation.

embedding

A dense float vector produced by the embedder. All memories in a collection must share the same dimensionality. You can provide a pre-computed embedding via StoreRequest.embedding, or let MAST generate one via the Embedder trait.

metadata

Arbitrary string key-value pairs. Useful for tagging memories with source, session ID, topic, or any domain-specific labels. Metadata is indexed and can be filtered during recall.

#![allow(unused)]
fn main() {
HashMap::from([
    ("source".into(), "conversation".into()),
    ("session".into(), "abc123".into()),
    ("topic".into(), "preferences".into()),
])
}

tier

One of four tiers that classify a memory’s lifecycle stage:

TierWeightPurpose
Core1.0Foundational knowledge, rarely changes
Active0.9Recent, frequently accessed (default)
Background0.7Older, less accessed
Archive0.5Historical, low relevance

Tiers affect recall scoring. See Compaction for tier promotion.

ttl

Optional time-to-live in seconds. A memory expires when now - created_at >= ttl. Expired memories are excluded from recall() results automatically. Call vacuum() to hard-delete expired memories.

compacted_at

Set when a memory has been compacted into a higher-tier synthesis. Compacted memories are excluded from recall() but remain visible in list() for provenance tracing.

parent_ids

Links a compacted memory to its source memories. This preserves provenance – you can always trace a high-tier insight back to the raw events that produced it.

StoreRequest

To create a memory, build a StoreRequest:

#![allow(unused)]
fn main() {
pub struct StoreRequest {
    pub collection: String,
    pub content: String,
    pub embedding: Option<Vec<f32>>,       // None = auto-embed
    pub metadata: HashMap<String, String>,
    pub tier: Tier,                         // defaults to Active
    pub ttl: Option<i64>,                   // None = no expiry
}
}

If embedding is None, MAST calls the provided Embedder to generate one. If Some, the provided vector is used directly.

Lifecycle

  1. Created via store() – assigned a ULID, embedded, indexed
  2. Recalled via recall() – access_count incremented, last_accessed updated
  3. Compacted via compact() – marked with compacted_at, hidden from recall
  4. Expired – excluded from recall when TTL elapsed
  5. Vacuumed via vacuum() – hard-deleted from storage and indexes
  6. Deleted via delete() – removed from storage and indexes immediately

Collections

Collections are namespaces that isolate memories, indexes, and graph edges from each other. Every memory belongs to exactly one collection.

What a Collection Provides

Each collection maintains its own:

  • Vector index (usearch HNSW) with a fixed dimensionality
  • Full-text index (BM25 posting lists)
  • Metadata index (inverted index)
  • Graph edges (forward and reverse indexes)
  • Memory count and stats

Creating Collections

Collections are created implicitly on first write. There is no explicit “create collection” operation. The first store() call to a new collection name creates it and sets its vector dimensions based on the first embedding.

#![allow(unused)]
fn main() {
// This creates the "user:alice" collection with 1536 dimensions
mast.store(
    StoreRequest {
        collection: "user:alice".into(),
        content: "Alice likes dark mode".into(),
        embedding: None,  // embedder produces 1536-dim vector
        ..Default::default()
    },
    &embedder,
).await?;
}

Dimension Enforcement

The first memory stored in a collection defines its vector dimensions. All subsequent memories must have embeddings with the same dimensionality. Mismatches are rejected with an error:

embedding dimensions 768 do not match collection dimensions 1536

Collection Info

Use info() to list all collections and their stats:

#![allow(unused)]

pub struct CollectionInfo {
    pub name: String,        // collection name
    pub dimensions: usize,   // vector dimensionality

}

for col in &collections {
    println!("{}: {} memories, {} dims", col.name, col.memory_count, col.dimensions);

Naming Conventions

Collection names are arbitrary strings. Common patterns:

"user:alice"               // all memories about a user
"agent:assistant"          // the agent's own memories
"user:alice:assistant"     // session-scoped memories
"project:acme"             // project-scoped memories

Isolation

Collections are fully isolated:

  • A recall() on collection A never returns results from collection B.
  • vacuum() only affects the specified collection.
  • snapshot() exports a single collection.
  • Graph edges are scoped to a collection.

Embeddings

MAST does not include an embedding model. Instead, it provides a pluggable Embedder trait that you implement or use a provided implementation.

The Embedder Trait

#![allow(unused)]
fn main() {
#[async_trait]
pub trait Embedder: Send + Sync {
    /// Embed a single text into a vector.
    async fn embed(&self, text: &str) -> Result<Vec<f32>, MastError>;

    /// Embed multiple texts in a batch (for efficiency).
    async fn embed_batch(&self, texts: &[String]) -> Result<Vec<Vec<f32>>, MastError>;

    /// Return the vector dimensionality.
    fn dimensions(&self) -> usize;
}
}

The Embedder is passed to store() and recall() as a reference. MAST calls it when:

  • store() is called without a pre-computed embedding (StoreRequest.embedding = None)
  • recall() is called with a text query (RecallRequest.query = Some(...)) and no query_embedding
  • store_batch() needs to embed items without pre-computed embeddings
  • compact() needs to embed the synthesized content

Writing a Custom Embedder

Implement the Embedder trait for any embedding provider:

#![allow(unused)]
fn main() {
use async_trait::async_trait;
use mast_core::embed::Embedder;
use mast_core::error::MastError;

struct MyEmbedder { /* ... */ }

#[async_trait]
impl Embedder for MyEmbedder {
    async fn embed(&self, text: &str) -> Result<Vec<f32>, MastError> {
        // Call your embedding service
        let vector = my_api_call(text).await
            .map_err(|e| MastError::Embedder(e.to_string()))?;
        Ok(vector)
    }

    async fn embed_batch(&self, texts: &[String]) -> Result<Vec<Vec<f32>>, MastError> {
        // Batch embed for efficiency, or fall back to sequential
        let mut results = Vec::with_capacity(texts.len());
        for text in texts {
            results.push(self.embed(text).await?);
        }
        Ok(results)
    }

    fn dimensions(&self) -> usize {
        768
    }
}
}

Search

MAST supports three search modes: Vector, FullText, and Hybrid. All searches are scoped to a single collection and return scored results sorted by relevance.

Search Modes

#![allow(unused)]
fn main() {
pub enum SearchMode {
    Vector,                              // Cosine similarity via usearch
    FullText,                            // BM25 keyword search
    Hybrid { vector_weight: f32, text_weight: f32 }, // Blended
}
}

Vector Search

Uses cosine similarity via the usearch HNSW index. Requires either a query (text to embed) or a query_embedding (pre-computed vector).

#![allow(unused)]
fn main() {
let results = mast.recall(
    RecallRequest {
        collection: "notes".into(),
        query: Some("machine learning concepts".into()),
        query_embedding: None,
        text_query: None,
        search_mode: SearchMode::Vector,
        limit: 10,
        filter: None,
        tier_weights: None,
        time_decay: None,
    },
    &embedder,
).await?;
}

Score formula: score = similarity * tier_weight * time_decay

Where:

  • similarity = 1.0 - cosine_distance
  • tier_weight from TierWeights (Core=1.0, Active=0.9, Background=0.7, Archive=0.5)
  • time_decay = 0.5^(age_secs / half_life_secs) (1.0 if no decay configured)

Full-Text Search

Uses BM25 scoring with a built-in tokenizer. The tokenizer lowercases text, splits on non-alphanumeric characters, removes tokens shorter than 2 characters, and filters stop words.

#![allow(unused)]
fn main() {
let results = mast.recall(
    RecallRequest {
        collection: "notes".into(),
        query: None,
        query_embedding: None,
        text_query: Some("dark mode preferences".into()),
        search_mode: SearchMode::FullText,
        limit: 10,
        filter: None,
        tier_weights: None,
        time_decay: None,
    },
    &embedder,
).await?;
}

Score formula: score = bm25_score * tier_weight * time_decay

BM25 parameters: k1 = 1.2, b = 0.75.

Full-text search does not require an embedder. The text_query field is used; if absent, query is used as fallback.

Hybrid Search

Runs both vector and full-text search, normalizes scores with min-max normalization, and blends them using configurable weights.

#![allow(unused)]
fn main() {
let results = mast.recall(
    RecallRequest {
        collection: "notes".into(),
        query: Some("dark mode".into()),
        query_embedding: None,
        text_query: Some("dark mode".into()),
        search_mode: SearchMode::Hybrid {
            vector_weight: 0.7,
            text_weight: 0.3,
        },
        limit: 10,
        filter: None,
        tier_weights: None,
        time_decay: None,
    },
    &embedder,
).await?;
}

Score formula: score = vector_weight * norm(vec_score) + text_weight * norm(ft_score)

Where norm() is min-max normalization to [0, 1] across the result set.

Metadata Filtering

All search modes support metadata filtering. Filters are applied after the initial search and before scoring.

fn main() {
pub enum MetadataFilter {

Time Decay

Apply exponential time decay to favor recent memories:

Example: with half_life_secs = 86400 (1 day), a 2-day-old memory scores 0.25x vs. a new one.

Exclusion Rules

Recall automatically excludes:

  • Memories with compacted_at.is_some() (already compacted)
  • Memories with expired TTL (now - created_at >= ttl)

Access Stats

After recall, all returned memories have their access_count incremented and last_accessed updated. This data feeds into compaction strategies.

Compaction

Compaction is MAST’s mechanism for evolving memories from raw events into distilled knowledge. It promotes memories from one tier to a higher tier by synthesizing multiple memories into new, higher-order insights.

How It Works

  1. Select candidates from the source tier based on a strategy
  2. Group into batches of max_batch_size
  3. Synthesize each batch via the Compactor trait (typically an LLM call)
  4. Store the synthesized memory in the target tier with parent_ids linking to sources
  5. Mark source memories as compacted (compacted_at timestamp set)

Compacted memories are hidden from recall() but remain in storage for provenance.

Tiers

TierPurposeDefault Weight
CoreFoundational knowledge, rarely changes1.0
ActiveRecent, frequently accessed0.9
BackgroundOlder, less accessed0.7
ArchiveHistorical, low relevance0.5

Compaction Strategies

#![allow(unused)]
fn main() {
pub enum CompactionStrategy {
    /// Compact memories older than a threshold
    Age { older_than_secs: i64 },

    /// Compact memories with zero access count
    AccessDecay,

    /// Combine age (>24h) and low access (<3)
    Hybrid,

    /// Compact specific memory IDs
    Manual { ids: Vec<Ulid> },
}
}

Age Strategy

Selects memories from the source tier where now - created_at > older_than_secs.

AccessDecay Strategy

Selects memories with access_count == 0 – never recalled since stored.

Hybrid Strategy

Selects memories that are both old (>24 hours) and rarely accessed (<3 times).

Manual Strategy

Selects specific memories by ID. Useful for explicit curation.

The Compactor Trait

#![allow(unused)]
fn main() {
#[async_trait]
pub trait Compactor: Send + Sync {
    async fn synthesize(&self, memories: &[Memory]) -> Result<CompactedMemory, MastError>;
}

pub struct CompactedMemory {
    pub content: String,
    pub metadata: HashMap<String, String>,
}
}

The Compactor receives a batch of source memories and produces a single synthesized output. This is not summarization – it is knowledge creation. The implementation typically calls an LLM.

Example: LLM-Based Compactor

#![allow(unused)]
fn main() {
struct LlmCompactor { client: OpenAIClient }

#[async_trait]
impl Compactor for LlmCompactor {
    async fn synthesize(&self, memories: &[Memory]) -> Result<CompactedMemory, MastError> {
        let prompt = format!(
            "Synthesize these memories into a single higher-order insight:\n{}",
            memories.iter().map(|m| m.content.as_str()).collect::<Vec<_>>().join("\n- ")
        );
        let content = self.client.complete(&prompt).await?;
        Ok(CompactedMemory { content, metadata: HashMap::new() })
    }
}
}

Provenance

Every compacted memory records its parent_ids. You can trace any high-tier memory back to the raw events that produced it:

#![allow(unused)]
fn main() {
let memory = mast.get("user:alice", &compacted_id)?.unwrap();
for parent_id in &memory.parent_ids {
    let parent = mast.get("user:alice", parent_id)?;
    // trace back to source
}
}

Safety

  • max_batch_size must be > 0 (validated, returns error otherwise)
  • If vector index insertion fails for the synthesized memory, the storage write is rolled back
  • Source memories are only marked as compacted after successful synthesis and storage

Graph

MAST includes a graph layer for modeling entity relationships alongside memories. Entities are connected by weighted, typed edges within a collection.

Data Model

#![allow(unused)]
fn main() {
pub struct Edge {
    pub id: Ulid,                // Unique edge ID
    pub collection: String,      // Scoped to a collection
    pub source: String,          // Source entity name
    pub target: String,          // Target entity name
    pub relation: String,        // Relation type (e.g., "prefers", "knows")
    pub weight: f32,             // Confidence / strength (0.0 to 1.0)
    pub memory_ids: Vec<Ulid>,   // Supporting memories
    pub created_at: i64,         // Creation timestamp
    pub updated_at: i64,         // Last update timestamp
}
}

Creating Edges

Use relate() to create or update an edge. If an edge with the same (source, target, relation) already exists, the weight and memory_ids are updated (upsert).

#![allow(unused)]
fn main() {
let edge_id = mast.relate(RelateRequest {
    collection: "user:alice".into(),
    source: "alice".into(),
    target: "dark_mode".into(),
    relation: "prefers".into(),
    weight: 0.9,
    memory_ids: vec![memory_id],
})?;
}

Upsert Behavior

#![allow(unused)]
fn main() {
// First call creates the edge
mast.relate(RelateRequest {
    source: "alice".into(),
    target: "dark_mode".into(),
    relation: "prefers".into(),
    weight: 0.7,
    ..
})?;

// Second call updates weight (same source+target+relation)
mast.relate(RelateRequest {
    source: "alice".into(),
    target: "dark_mode".into(),
    relation: "prefers".into(),
    weight: 0.95,  // updated
    ..
})?;
}

Removing Edges

#![allow(unused)]
fn main() {
mast.unrelate("user:alice", "alice", "dark_mode", "prefers")?;
}

Returns an error if no matching edge exists.

Traversal

BFS (breadth-first search) traversal from a starting entity:

#![allow(unused)]
fn main() {
let edges = mast.traverse(TraverseRequest {
    collection: "user:alice".into(),
    start: "alice".into(),
    max_depth: 3,
    relation_filter: Some("prefers".into()),  // optional
    min_weight: Some(0.5),                     // optional
})?;

for edge in &edges {
    println!("{} --[{}]--> {} (w={:.2})", edge.source, edge.relation, edge.target, edge.weight);
}
}

TraverseRequest Fields

FieldTypeDescription
collectionStringCollection to search
startStringStarting entity name
max_depthusizeMaximum BFS depth
relation_filterOption<String>Only follow edges with this relation
min_weightOption<f32>Only follow edges above this weight

Traversal visits each entity at most once (cycle-safe). It returns all edges encountered during BFS, not just the final frontier.

Subgraph

Get all edges in a collection:

#![allow(unused)]
fn main() {
let graph = mast.subgraph("user:alice")?;
println!("{} edges in collection", graph.edges.len());
}

Returns a Graph struct:

#![allow(unused)]
fn main() {
pub struct Graph {
    pub collection: String,
    pub edges: Vec<Edge>,
}
}

Storage

Edges are stored in redb with three tables:

TableKeyValue
EDGES(collection, edge_id)Serialized Edge
EDGE_INDEX_FWD(collection, source, relation)List of edge IDs
EDGE_INDEX_REV(collection, target, relation)List of edge IDs

Forward and reverse indexes enable O(1) entity lookups in both directions.

Linking Edges to Memories

The memory_ids field connects an edge to the memories that support it. This creates a bridge between the flat memory store and the entity graph:

#![allow(unused)]
fn main() {

    content: "Alice told me she prefers dark mode".into(),
    ..
}, &embedder).await?;

// Create a graph edge linking back to the memory
mast.relate(RelateRequest {
    source: "alice".into(),
    target: "dark_mode".into(),
    relation: "prefers".into(),
    weight: 0.9,
    memory_ids: vec![memory.id],
    ..
})?;
}

Embedder Protocol

MAST’s Python bindings accept any object with an embed(text) -> list[float] method and a dimensions() -> int method:

class MyEmbedder:
    def embed(self, text: str) -> list[float]:
        # Call your embedding API
        return openai.embeddings.create(input=text, model="text-embedding-3-small").data[0].embedding

    def embed_batch(self, texts: list[str]) -> list[list[float]]:
        # Optional: batch embedding for efficiency
        result = openai.embeddings.create(input=texts, model="text-embedding-3-small")
        return [d.embedding for d in result.data]

    def dimensions(self) -> int:
        return 1536

MAST provides a C-compatible FFI via the mast-ffi crate. This enables integration with any language that can call C functions (Go, Swift, Ruby, etc.).

Core Concepts

MastHandle

An opaque pointer to the MAST instance. Created with mast_open(), freed with mast_close().

Error Handling

All functions that can fail accept a MastFfiError** out-parameter. On error, the pointer is set to an allocated error struct:

typedef struct {
    int code;       // Error category (see table below)
    char* message;  // Human-readable error message
} MastFfiError;
CodeCategory
1Storage
2Index
3Embedder
4NotFound
5InvalidInput
6Serialization
7Compaction
8Graph
9Snapshot

Always check the error pointer after each call and free it with mast_free_error().

Embedder Callbacks

The FFI uses a vtable of function pointers for embedding:

typedef struct {
    // Required: embed a single text
    float* (*embed)(
        void* user_data,
        const char* text,
        size_t* out_len,
        MastFfiError** err
    );

    // Optional: batch embed (falls back to sequential if NULL)
    float** (*embed_batch)(
        void* user_data,
        const char** texts,
        size_t count,
        size_t* out_lens,
        MastFfiError** err
    );

    // Optional: return dimensions
    size_t (*dimensions)(void* user_data);

    // Opaque pointer passed to all callbacks
    void* user_data;
} MastEmbedderVtable;

The embed callback must return a heap-allocated float* array. MAST takes ownership via Vec::from_raw_parts.

#include <stdlib.h>
#include <string.h>

typedef struct MastFfiError MastFfiError;

);
extern void mast_free_error(MastFfiError* err);
extern void mast_free_store_result(MastStoreResult* result);

int main() {
    MastFfiError* err = NULL;

    // Open database
    MastHandle* db = mast_open("test.mast", &err);
    if (err) {
        fprintf(stderr, "Error: %s\n", err->message);
        mast_free_error(err);
        return 1;
    }

    // Set up embedder vtable
    MastEmbedderVtable vtable = {
        .embed = my_embed_fn,
        .embed_batch = NULL,  // optional
        .dimensions = my_dims_fn,
        .user_data = my_context,

    MastStoreResult* result = mast_store(
        db, "notes", "hello world",

    if (err) {
        fprintf(stderr, "Store error: %s\n", err->message);
        mast_free_error(err);
    } else {
        printf("Stored: %s\n", result->id);
        mast_free_store_result(result);
    }

    mast_close(db);
    return 0;
}

Snapshots

MAST supports exporting and importing collections as JSONL (JSON Lines) files. This enables backup, migration, and portability between MAST instances.

JSONL Format

A snapshot file consists of:

  1. Header line – JSON object with metadata
  2. Data lines – one JSON object per memory or edge

Header

FieldDescription
mast_snapshotFormat version (currently “1.0”)

{"type":"memory","data":{"id":"01H...","collection":"user:alice","content":"Alice prefers dark mode","embedding":[0.1,0.2,...],"metadata":{"source":"conversation"},"tier":"Active","created_at":1700000000,"access_count":3,"last_accessed":1700001000,"ttl":null,"compacted_at":null,"parent_ids":[]}}

Edge Lines

{"type":"edge","data":{"id":"01H...","collection":"user:alice","source":"alice","target":"dark_mode","relation":"prefers","weight":0.9,"memory_ids":[],"created_at":1700000000,"updated_at":1700000000}}

Performance

Guidelines for optimizing MAST performance.

Embedding Dimensions

The choice of embedding dimensions directly impacts memory usage, index size, and search speed.

DimensionsModel ExampleIndex Memory per VectorUse Case
256Custom~1 KBPrototyping, small datasets
768many open-source models~3 KBBalanced quality/performance
1536OpenAI text-embedding-3-small~6 KBProduction, high quality
3072OpenAI text-embedding-3-large~12 KBMaximum quality

Lower dimensions = faster search + less memory. Use the smallest dimension that meets your quality requirements.

Batch Operations

Use store_batch() instead of repeated store() calls:

  • embed_batch() is called once instead of N individual embed calls
  • Reduces round trips to embedding APIs
  • Single transaction for all writes
#![allow(unused)]
fn main() {
// Prefer this:
mast.store_batch(BatchStoreRequest {
    collection: "notes".into(),
    items: items,  // vec of BatchStoreItem
}, &embedder).await?;

// Over this:
for item in items {
    mast.store(StoreRequest { .. }, &embedder).await?;
}
}

Search Tuning

Overfetch Factor

MAST internally fetches limit * 3 + 10 candidates from the vector/full-text index, then filters and re-ranks. This means:

  • Setting limit: 5 actually searches for ~25 candidates
  • This handles filtering out compacted/expired memories without missing results
  • Higher limits incur proportionally more index search cost

Search Mode Selection

ModeBest ForCost
VectorSemantic similarityOne embedding + HNSW search
FullTextExact keyword matchingNo embedding needed, posting list lookups
HybridBest overall relevanceBoth vector + full-text, then merge

Full-text search is faster than vector search because it does not require an embedding call.

Metadata Filters

Metadata filters run after the initial vector/full-text search. For vector search with metadata filters, MAST uses filtered_search on the HNSW index, which pre-filters candidates. This is efficient for selective filters but may be slower for very broad filters.

Memory Management

Vector Index Caching

Vector indexes are held in memory during the lifetime of the Mast instance. The index is persisted to redb on close() or Drop. Keeping the instance open avoids repeated index deserialization.

Index Capacity

usearch pre-allocates capacity in blocks of 1024 vectors. After loading from a buffer, it reserves current_size + 1024 additional slots. This avoids frequent reallocations for typical workloads.

Storage

redb Characteristics

  • Single-file ACID database
  • Copy-on-write B-tree
  • No write-ahead log to manage separately
  • Good for read-heavy workloads
  • Single-writer, multiple-reader

Data Size Estimates

Per memory, storage overhead is approximately:

ComponentSize
Memory record (bincode)~content_len + dims*4 + metadata + 200 bytes overhead
Vector index entry~dims * 4 bytes + HNSW graph edges
Full-text posting entries~tokens * 30 bytes
Metadata index entries~metadata_pairs * 40 bytes
ULID/seq mappings~64 bytes

Vacuum and Compaction

Vacuum

Run vacuum() periodically on collections with TTL-bearing memories. Vacuuming removes expired memories from storage and indexes, reclaiming space.

Compaction

Compaction reduces the number of active memories by synthesizing them into higher-tier summaries. This improves recall speed (fewer candidates to search) and reduces storage size.

Recommended compaction strategy:

  1. Start with CompactionStrategy::Age { older_than_secs: 86400 } (1 day)
  2. Set max_batch_size to 5-20 memories (larger batches produce better synthesis but consume more LLM tokens)
  3. Run as a periodic background job

Close and Flush

Always call close() or let Drop run. If the process exits before either happens, vector index updates since the last flush are lost (storage data is safe due to redb’s ACID properties).

#![allow(unused)]
fn main() {
// Explicit close with error handling
mast.close()?;

// Or rely on Drop (logs errors but does not panic)
drop(mast);
}

CLI Performance Tips

When using the CLI for batch operations, keep the database handle open as long as possible. Each CLI invocation opens and closes the database, which includes index serialization/deserialization.

For bulk operations, prefer the Rust API or language bindings over repeated CLI calls.

Architecture

MAST’s internal architecture consists of three layers: storage, indexing, and serialization.

Workspace Layout

crates/
+-- mast-core/         Core engine (storage, index, types, config, graph, compaction, snapshot)
+-- mast-embed-openai/ OpenAI embedder implementation
+-- mast-cli/          Command-line interface
+-- mast-ffi/          C FFI bindings
+-- mast-py/           Python bindings (PyO3)
+-- mast-node/         Node.js bindings (napi-rs)

mast-core has zero vendor dependencies for embeddings. The Embedder trait is the boundary – all embedding logic lives outside the core.

Storage Layer (redb)

All persistent data lives in a single redb database file. redb is an embedded key-value store with ACID transactions, copy-on-write B-trees, and a single-writer/multiple-reader concurrency model.

ULID-to-Seq Mapping

usearch requires u64 keys, but MAST uses ULIDs (128-bit). The ulid_to_seq and seq_to_ulid tables provide bidirectional mapping. Each collection maintains an auto-incrementing seq counter.

Index Layer

Vector Index (usearch)

Per-collection HNSW indexes using cosine distance. Indexes are:

  • Held in memory during runtime for fast search
  • Serialized to redb’s vector_index table on close() or Drop
  • Deserialized from redb on open() (via load_from_buffer)
  • After loading, capacity is reserved as current_size + 1024 to allow inserts

Configuration:

#![allow(unused)]
fn main() {
IndexOptions {
    dimensions: N,
    metric: MetricKind::Cos,
    quantization: ScalarKind::F32,
    ..Default::default()
}
}

The IndexManager manages per-collection vector indexes, creating them on first write and loading existing ones from storage.

Full-Text Index (BM25)

Built-in BM25 implementation stored in redb. No external full-text library.

Tokenizer:

  1. Lowercase the text
  2. Split on non-alphanumeric characters
  3. Remove tokens shorter than 2 characters
  4. Remove stop words (common English words)

Posting lists are stored per-term in the ft_posting table. Each entry contains:

#![allow(unused)]
fn main() {
pub struct PostingEntry {
    pub ulid_bytes: [u8; 16],   // Document ID
    pub term_freq: u32,          // Term frequency in this document
    pub field_length: u32,       // Total tokens in this document
}
}

BM25 scoring (parameters: k1=1.2, b=0.75):

IDF = ln((N - df + 0.5) / (df + 0.5) + 1.0)
TF  = (tf * (k1 + 1)) / (tf + k1 * (1 - b + b * dl / avgdl))
score = sum(IDF * TF for each query term)

Metadata Index

Inverted index mapping (collection, key, value) to lists of ULID bytes. Supports Eq, In, And, and Or filters with arbitrary nesting.

Serialization

Memory Serialization (Versioned Envelope)

Memories use a versioned serialization format for forward compatibility:

Byte 0Format
0x01V1: bincode-serialized full Memory struct
OtherV0: raw bincode of legacy struct (no ttl, compacted_at, parent_ids)

V0 data is auto-migrated on read: ttl=None, compacted_at=None, parent_ids=[]. No scan-and-rewrite migration is needed.

#![allow(unused)]
fn main() {
pub fn serialize_memory(m: &Memory) -> Result<Vec<u8>, MastError> {
    let payload = bincode::serialize(m)?;
    let mut buf = Vec::with_capacity(1 + payload.len());
    buf.push(0x01);  // VERSION_V1
    buf.extend_from_slice(&payload);
    Ok(buf)
}
}

Edge Serialization

Edges use raw bincode (no versioned envelope).

Snapshot Format

JSONL (JSON Lines) with serde_json. Each line is either a {"type":"memory","data":{...}} or {"type":"edge","data":{...}} object, preceded by a header line.

Write Path

  1. Generate ULID
  2. Compute embedding (if not provided)
  3. Write memory to memories table (redb transaction)
  4. Allocate seq key, write ULID-to-seq and seq-to-ULID mappings
  5. Add vector to usearch index (in-memory)
  6. Update metadata index (redb)
  7. Update full-text index (redb)
  8. On failure at step 5: compensating rollback (delete from storage)

Read Path (Recall)

  1. Embed query text (if not pre-computed)
  2. Search vector index (or full-text index, or both for hybrid)
  3. For vector: apply metadata filter via filtered_search
  4. Map seq keys back to ULIDs
  5. Load memories from storage
  6. Filter out compacted and expired memories
  7. Compute score: similarity * tier_weight * time_decay
  8. Sort by score descending, truncate to limit
  9. Update access stats on returned memories

Drop and Flush

Mast implements Drop to flush all in-memory vector indexes to redb. The close() method does the same with error propagation. If neither runs (process crash), vector index updates since the last flush are lost, but all storage data (memories, edges, metadata, full-text) is safe due to redb’s ACID guarantees.
